# 백엔드 → 프론트 인수인계 (PR #505 머지, 2026-08-20)

백엔드 세션이 작성. 이 문서 하나만 읽으면 지금 프론트가 할 일이 다 나온다.
반대 방향 문서(`backend-handoff-2026-08-20.md`)는 처리가 끝났으니 다시 열지 않아도 된다.

---

## 1. 막혀 있던 것 둘이 열렸다

### 잔액 (이슈 #502)

`PracticeAttemptResponse`를 돌려주는 **쓰기 경로 네 곳이 모두 실제 잔액**을 싣는다.

| 호출 | `tutorialCashBalance`·`tutorialAvailableCash`·`tutorialRealizedPnl` |
|---|---|
| `PUT /api/education/practice/attempts/{market}` (진입) | 실값 |
| `POST .../attempts/{market}/restart` (재시작) | 실값 |
| `PUT .../attempts/{market}/instrument` (종목 선택) | **실값 (새로 열림)** |
| `PUT .../attempts/{market}/exit-preset` (프리셋 선택) | **실값 (새로 열림)** |
| `GET /api/education/practice`의 `attempt` 필드 | **여전히 `0`** |

**마지막 줄이 중요하다.** 진행 조회는 tick과 함께 폴링되는 경로라 호출마다 계좌를 다시 읽지
않기로 했다. 그 `0`은 "잔고가 0"이 아니라 **"이 응답은 계좌를 조회하지 않았다"** 는 뜻이다.
**잔액은 위 네 응답에서 받아 상태로 들고 있어야 하고, 진행 조회 응답의 그 세 필드로 잔액 박스를
그리면 안 된다.**

→ 9차 E의 "주문 가능 잔액 + 10/25/50/75/최대 퍼센트 버튼"은 이제 막힌 것이 없다.

### 단계 진행 판정 (이슈 #503)

`GET /api/education/practice` 최상위에 `tutorialStageProgress`가 생겼다.

```json
"tutorialStageProgress": {
  "marketBuySellCompleted": true,
  "limitBuySellCompleted": false,
  "exitPresetSelected": false
}
```

| 필드 | `true`가 되는 조건 |
|---|---|
| `marketBuySellCompleted` | 이 실행에 시장가 매수 체결이 있고 **사용자가 낸** 시장가 매도 체결도 있다 |
| `limitBuySellCompleted` | 이 실행에 지정가 매수와 지정가 매도가 둘 다 있다 |
| `exitPresetSelected` | 이 실행에서 프리셋을 직접 골랐는가 (`PUT .../exit-preset` 호출 여부) |

**반드시 알아야 할 네 가지.**

1. **`null`이 되지 않는다.** attempt가 없는 경로(legacy chain, 즐겨찾기만, 미착수)와 종목 미선택도
   세 값 모두 `false`인 객체로 온다. null 분기를 만들지 마라.
2. **판정 범위는 현재 실행 세대(run)다.** 재시작하면 셋 다 `false`로 돌아간다.
3. **손절·익절이 자동으로 청산한 매도는 세지 않는다.** 프리셋에 잘린 사용자는 시장가 단계를 아직
   못 마친 것으로 나온다 — 의도된 동작이다.
4. **`limitBuySellCompleted`는 주식(STOCK)에서 영원히 `false`다.** 지정가 주문 경로가 코인 전용이라
   주식 튜토리얼에는 이 단계를 통과할 수단이 없다. **진행바를 시장 구분 없이 쓰면 주식에서 막힌다.**

**이 값으로 잠금 UI를 그려라. 로컬로 세지 마라** — 새로고침해도 서버가 다시 판정한다.

### 진입별 주문 유형

`entries[]`의 각 항목에 `buyOrderType`(`"MARKET"` | `"LIMIT"`)이 생겼다. 완료 화면에서 "이 진입은
시장가, 저 진입은 지정가"를 구분해 그릴 수 있다.

⚠️ **그 진입을 "연" 매수의 유형이다.** 같은 항목의 `buyQuantity`·`buyPrice`는 진입 구간의 매수를
전부 합산한 값이라 기준이 다르다. **"이 수량을 어떤 방식으로 샀는가"로 읽으면 안 된다.**

### 재진입 UI — 더 이상 막을 이유가 없다

D34에서 유보했던 "evidence 체인이 재진입을 아는가"는 전제가 틀렸음이 확인됐다(D35 참고).
재진입해도 두 번째 holding은 생기지 않고, 관찰 필터 기준선이 첫 진입에 고정돼 있어 재매수에
이전 관찰이 사라지지 않는다. 통합 테스트가 매수→관찰3→손절→재매수→익절→복기→완료를 완주한다.

## 2. 프론트가 정해 줘야 백엔드가 다음 단계를 시작한다 — 3건

다음 백엔드 작업은 **2단계(주문 방법 학습)를 3단계 대본에서 분리하는 것**이다(이슈 #479, spec 049).
확정된 설계는 이렇다.

- 2단계는 **전용 짧은 대본**을 쓴다. 기준가 10만원, ±12% 사인파, 한 바퀴 실제 1분, 전체 실제 8분.
  가격 범위는 **90,000~110,000원**이고 서버가 응답으로 내려준다(하드코딩 금지).
- 2단계에는 **사건이 없다** — `causeStatus`는 항상 `NONE_KNOWN`, `revealedEvents`는 빈 배열이다.
- 2단계에서는 **자동 손절·익절이 작동하지 않는다.** 손절·익절은 3단계에서 배우는 것이기 때문이다.
- 지정가 접수를 가격 때문에 거부하지 않는다. **범위 밖에 걸어 미체결을 보여주고, 범위 안에서 다시
  걸면 체결되는 흐름**을 의도적으로 넣는다("더 기다리라"고 붙잡지 않는다 — 취소·재접수가 자유롭다).

여기서 **프론트 합의가 필요한 것이 셋**이다.

### (1) 화면 게이팅을 어디까지 할 것인가

2단계 화면에서는 손절·익절 컨트롤을 아예 숨길지, 비활성으로 보여줄지. 3단계에서는 반대로 주문
방법 선택을 어떻게 다룰지. **서버는 판정(`tutorialStageProgress`)과 거부(409)까지만 제공하고
무엇을 감출지는 화면이 정한다.**

### (2) 2단계 → 3단계 전환을 누가 언제 호출하는가

백엔드가 전용 엔드포인트(`POST .../attempts/{market}/advance-script`)를 만든다. 조건(보유 없음)만
검사한다. **사용자가 "3단계로 가기" 버튼을 눌러 호출할지, 조건 충족 시 화면이 자동으로 호출할지**를
정해 달라.

### (3) `scenarioStage`에 새 값 `"ORDER_BASICS"`가 생긴다

지금 계약은 `IDLE_ENTRY|ACT1|ACT2|IDLE_REENTRY|ACT3|ACT4|FINISHED` 7개인데 2단계 대본이 들어오면
여덟 번째 값이 나간다. **이 값을 받았을 때 화면이 무엇을 보여줄지** 정해 달라(막 표시가 의미 없는
구간이다).

## 3. 아직 안 되는 것

**순서 강제는 아직 없다.** 잘못된 순서의 주문을 서버가 409로 거부하지 않는다. 사용자가 API를 직접
불러 순서를 건너뛸 수 있지만 이건 보안이 아니라 학습 순서라, 판정만으로 화면은 정확히 그려진다.
거부는 spec 049 구현에 포함된다.

**이슈 #491(잠금 교착)은 안 고쳐졌다.** 재시작과 tick 폴링이 겹칠 때 500이 날 수 있다. 잠금을
실측했지만 교착 쌍을 특정하지 못해 추측으로 고치지 않았다. **프론트 완화는 계속 필요하다** —
재시작 요청 중에는 tick 폴링을 멈추고, 500이 오면 재시도 버튼을 준다.
