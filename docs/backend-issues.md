# 백엔드에 제기할 이슈 (프론트에서 우회하지 않는다)

작성 2026-08-08. 근거는 `docs/backend-contracts/` 세 문서와 `finplay-team/finplay`의
`docs/api-contracts.md`·`api-routes.md`·`docs/specs/*/spec.md`다.

**이 문서의 원칙.** 프론트엔드는 백엔드 계약의 결함을 화면에서 감추지 않는다. 우회 코드로 덮으면
결함이 계약에 남고 다음 소비자가 같은 함정을 다시 밟는다. 아래 항목은 **백엔드에서 고쳐야 하는 것**이고,
프론트는 고쳐질 때까지 동작을 정직하게 노출하거나 기능을 내보내지 않는다.

도메인 구분은 `api-routes.md`의 "도메인" 칼럼을 따른다.
우선순위는 **P1 = 데이터 손실·기능 불가**, **P2 = 사용자에게 잘못된 정보**, **P3 = 계약 일관성**이다.

| 도메인 | 이슈 수 | P1 | P2 | P3 |
|---|---|---|---|---|
| community | 6 | 4 | 1 | 1 |
| market (시세·캔들) | 2 | 0 | 1 | 1 |
| ranking | 2 | 0 | 2 | 0 |
| journal | 1 | 0 | 0 | 1 |
| feedback (AI) | 3 | 0 | 0 | 3 |
| order·journal·ranking 공통 | 1 | 0 | 0 | 1 |
| **합계** | **15** | **4** | **4** | **7** |

> `order` 도메인의 지정가(LMT-001~005)·`watchlist` 계약 검토는 아직 진행 중이다.
> 끝나면 이 문서에 도메인 절을 추가한다.

## community

### C-1 [P1] 전 응답에 `authorId`가 없어 소유 판정이 불가능하다

- **현상.** 게시물·댓글 응답 어디에도 작성자 식별자가 없다. `authorNickname` 문자열뿐이다.
- **결과.** 클라이언트가 "내 글"을 판정할 방법이 닉네임 비교밖에 없다. 닉네임을 변경하면
  (`PATCH /api/auth/me/nickname`은 실제로 제공된다) **과거 글·댓글의 소유 판정이 전부 깨진다.**
  수정·삭제 버튼이 사라지거나 남의 글에 뜬다.
- **왜 프론트로 못 고치는가.** 응답에 없는 정보는 만들 수 없다. `403 FORBIDDEN`을 최종 권위로 두는
  현재 방식은 "눌러 보고 실패하면 안다"는 것이라 버튼 표시 자체를 옳게 만들지 못한다.
- **요청.** 게시물·댓글 응답에 `authorId`(회원 PK)를 추가한다. `GET /api/auth/me`가 이미 `id`를 주므로
  클라이언트가 정확히 비교할 수 있다.

### C-2 [P1] `PATCH /api/community/posts/{postId}`가 `instrumentId` 생략 시 종목 태그를 삭제한다

- **현상.** `api-contracts.md:293`이 `instrumentId`를 생략하거나 `null`로 보내면 **기존 태그를 해제한다**고
  명시한다. 즉 제목만 고치려는 요청이 태그를 지운다.
- **결과.** PATCH의 의미론(부분 수정) 위반이다. 모든 클라이언트가 "수정 전 값을 다시 실어 보내기"를
  기억해야 하며, 한 번 잊으면 조용한 데이터 손실이다. 변경 이력이 없어 되돌릴 수 없다.
- **요청.** 둘 중 하나로 확정한다.
  1. `instrumentId` 키가 **없으면 보존**, 명시적 `null`이면 해제 (JSON Merge Patch 관례)
  2. 또는 전체 교체임을 계약에 못박고 메서드를 `PUT`으로 바꾼다

### C-3 [P1] 부모 댓글 삭제가 타인의 대댓글까지 CASCADE로 지운다

- **현상.** `DELETE /api/community/comments/{commentId}`가 자식 대댓글을 `ON DELETE CASCADE`로 함께 삭제한다.
- **결과.** 내 댓글을 지우면 **다른 회원이 쓴 대댓글이 예고 없이 사라진다.** 그 회원에게는 자기 글을
  지킬 방법도, 삭제됐다는 통지도 없다.
- **요청.** 자식이 있는 부모 댓글은 tombstone(내용만 "삭제된 댓글입니다"로 치환, 행 유지)으로 처리한다.
  일반적인 게시판 관례이며 자식 소유자의 데이터를 보존한다.

### C-4 [P1] 댓글 조회에 페이지네이션이 없다

- **현상.** `GET /api/community/posts/{postId}/comments`가 bare array이고 개수 상한이 문서에 없다.
  COM-005로 `replies` 중첩이 추가된 뒤에도 그대로다.
- **결과.** 댓글이 많은 글에서 응답 크기가 무한히 커진다. 중첩이 생겨 배열 하나에 담기는 총량이 더 늘었다.
- **요청.** 부모 댓글 기준 커서 페이지네이션을 추가한다
  (`GET /api/orders`·`/api/journal`이 이미 쓰는 방식과 동일하게).

### C-5 [P2] 종목 태그 검증 400이 실패 사유를 구분하지 않는다

- **현상.** 존재하지 않는 종목과 `tradable=false`(거래정지) 종목이 **같은 `VALIDATION_ERROR`**로 온다.
  계약 문서가 "두 사유를 구분하지 않는다"고 명시한다.
- **결과.** 클라이언트가 사용자에게 무엇을 고쳐야 하는지 말해 줄 수 없다. `message`는 불안정 계약이라
  화면에 쓰지 않기로 이미 정해져 있어(4차 리팩터 결정) `code`만으로는 분기가 불가능하다.
- **요청.** `INSTRUMENT_NOT_FOUND`와 `INSTRUMENT_NOT_TRADABLE`로 코드를 분리한다.

### C-6 [P3] `api-routes.md`가 단건 게시물 조회에서 COM-004를 누락했다 (문서 정합)

- **현상.** `api-routes.md:35`의 `GET /api/community/posts/{postId}` 행에 COM-004 표기가 없는데
  `api-contracts.md`의 같은 엔드포인트는 태그 3필드를 반환한다고 명시한다.
- **요청.** 라우트 지도의 Spec 칼럼에 `022 COM-004`를 추가한다.

## market (시세·캔들)

### M-1 [P2] 집계 캔들의 `sourceTime`이 거래일이 아닌 날짜를 라벨로 반환한다

- **현상.** `interval=1w`·`1M`에서 `sourceTime`이 버킷 시작(월요일·1일) `T00:00:00`인데,
  **그 날이 거래일이 아니어도** 그 값을 준다. 또 거래일이 없는 주·월은 응답에서 통째로 빠져
  달력 연속성이 없다.
- **결과.** 축 라벨이 실제로 거래가 없던 날짜를 가리킨다. 사용자가 "이 날 거래가 있었다"고 오해한다.
- **요청.** 버킷의 **첫 실제 거래일**을 `sourceTime`으로 주거나, 버킷 경계와 대표 거래일을
  별도 필드로 분리한다.

### M-2 [P3] 캔들 `from`/`to` 시맨틱이 시장·interval마다 3종이다

- **현상.**
  - 주식 `1m` — 시각만 의미 있음 (날짜 무시)
  - 주식 `1d`·`1w`·`1M` — 날짜만 의미 있음 (시각 무시)
  - 코인 전체 — 전체 datetime
- **결과.** **같은 `from`/`to` 쌍이 주식에서는 통과하고 코인에서는 400이 된다.** 클라이언트가
  시장·interval 조합마다 다른 포맷을 만들어야 한다.
- **요청.** 전 조합에서 full datetime을 받고 서버가 내부적으로 절삭한다.

## ranking

### R-1 [P2] 랭킹의 `realizedPnl`과 계좌 요약의 `realizedPnl`이 다른 값을 낼 수 있다

- **현상.** `GET /api/rankings`·`/rankings/me`는 Redis ZSET score를 그대로 노출하고,
  `GET /api/accounts/summary`는 DB 값을 준다.
- **결과.** 같은 이름의 필드가 같은 화면에서 다른 숫자로 보인다. 사용자는 어느 쪽이 맞는지 알 수 없다.
- **요청.** 정본을 하나로 정하고(DB 권장), 랭킹은 순위 산출에만 ZSET을 쓰고 금액은 정본에서 읽는다.
  또는 응답에 집계 기준 시각(`asOf`)을 넣어 불일치가 시점 차이임을 드러낸다.

### R-2 [P2] Redis 조회 장애가 랭킹을 500으로 떨어뜨린다 (폴백 없음)

- **현상.** 랭킹 조회 시 Redis 장애는 `500 INTERNAL_ERROR`이고 폴백 정책이 없다.
- **참고.** AI 피드백은 같은 상황을 "Redis 장애는 전부 삼켜 캐시 미스로 취급"(ADR-0015)으로 처리한다.
  **같은 시스템 안에서 정책이 반대다.**
- **요청.** 랭킹도 DB 폴백 또는 명시적 `UNAVAILABLE` 상태 응답으로 통일한다.

## journal

### J-1 [P3] `journalId`가 매수·매도 회고 사이에서 중복될 수 있다

- **현상.** 두 테이블의 AUTO_INCREMENT가 별개라 같은 `journalId` 값이 매수 회고와 매도 회고에
  동시에 존재할 수 있다. 목록(`GET /api/journal`)은 `journalId`를 노출하지 않고
  `journalType` + 체결 ID로 식별하게 되어 있는데, **상세·수정 응답에는 `journalId`가 있다.**
- **결과.** 응답에 있는 식별자를 단독 키로 쓰면 충돌한다. "노출하지 않는다"는 회피이지 해결이 아니다.
- **요청.** `journalId`를 응답에서 제거하거나, `journalType`을 접두로 붙인 전역 유일 식별자로 만든다.

## feedback (AI 피드백)

### F-1 [P3] 같은 상황(재생세션 미준비)에 뉴스와 브리핑이 다른 상태값을 낸다

- **현상.** 재생세션 미준비 시 종목 뉴스(Part C)는 `NOT_YET`, 개장 전 브리핑(Part D)은 `EMPTY`다.
  spec 012 §C-4가 "의도된 차이"라고 명시한다.
- **결과.** 의도는 이해되지만(브리핑이 없는 날은 정상, 뉴스는 아직 안 열림) 클라이언트가 두 경로를
  공통 헬퍼로 처리할 수 없고, 실수하면 조용히 틀린 문구가 뜬다.
- **요청.** 최소한 원인 필드(`reason`)를 별도로 주어 상태값과 원인을 분리한다.

### F-2 [P3] `EMPTY`·`UNAVAILABLE` 상태에서도 `items`가 채워진다

- **현상.** §C-4 판정 순서 4·5번(요약 행 없음 / `summary`가 `NULL`)에서 `status`는 비어 있음을
  뜻하는 값인데 `items`는 채워진다. 또 `EMPTY`의 두 원인(기사 0건 / 요약 행 없음)은
  **응답 필드로 구분할 수 없고** `items.length`로만 추론 가능하다.
- **결과.** `status !== 'READY'`로 빈 상태를 그리는 자연스러운 구현이 **목록을 통째로 잃는다.**
- **요청.** 요약 상태(`summaryStatus`)와 목록 상태를 분리한다. 요약이 없어도 기사 목록은 유효하다.

### F-3 [P3] `originTradeDate=null`이 두 가지를 동시에 의미한다

- **현상.** `GET /api/instruments/{id}/price-moves`는 status enum이 없고, `originTradeDate=null`이
  **"재생세션 미준비"와 "코인 종목"** 둘 다를 뜻한다.
- **결과.** 클라이언트가 종목의 `market`을 별도로 조회해야 문구를 고를 수 있다. 응답만으로는 판별 불가.
- **요청.** `market` 필드를 응답에 넣거나 다른 두 경로처럼 `status` enum을 추가한다.

## order · journal · ranking 공통

### X-1 [P3] `limit` 범위 밖 처리 정책이 엔드포인트마다 다르다

- **현상.**
  - `GET /api/rankings` — 컨트롤러가 거부하지 않고 서비스가 클램핑 (생략·0 이하 → 10, 51 이상 → 50)
  - `GET /api/trades`·`GET /api/orders`·`GET /api/journal` — 범위 밖은 `400`
- **결과.** 계약 문서가 "의도적으로 다르다"고 적어 두었지만, 소비자 입장에서는 같은 이름의
  파라미터가 엔드포인트마다 다르게 동작하는 것이다. 공통 목록 컴포넌트를 만들 수 없다.
- **요청.** 한쪽으로 통일한다. 클램핑이 더 관대하므로 클램핑 권장.
