# 백엔드에 제기할 이슈 (프론트에서 우회하지 않는다)

작성 2026-08-08. 근거는 `docs/backend-contracts/` 세 문서와 `finplay-team/finplay`의
`docs/api-contracts.md`·`api-routes.md`·`docs/specs/*/spec.md`다.

**이 문서의 원칙.** 프론트엔드는 백엔드 계약의 결함을 화면에서 감추지 않는다. 우회 코드로 덮으면
결함이 계약에 남고 다음 소비자가 같은 함정을 다시 밟는다. 아래 항목은 **백엔드에서 고쳐야 하는 것**이고,
프론트는 고쳐질 때까지 동작을 정직하게 노출하거나 기능을 내보내지 않는다.

도메인 구분은 `api-routes.md`의 "도메인" 칼럼을 따른다.
우선순위는 **P1 = 데이터 손실·기능 불가**, **P2 = 사용자에게 잘못된 정보**, **P3 = 계약 일관성**이다.

## community

### C-1 [P1] 전 응답에 `authorId`가 없어 소유 판정이 불가능하다

> **IMPRECISE — P1 → P3 으로 낮춘다. 결과 주장이 거짓이었다.**
> `api-contracts.md:307`이 "작성자는 fetch join 으로 함께 조회"라고 명시한다 — 댓글 작성자는
> 저장 시점 스냅샷이 아니라 **조회 시점 조인**이다. 게다가 닉네임은 시점 유일이다
> (`:73`, 중복은 409 `DUPLICATE_RESOURCE`). 그래서 닉네임을 바꾸면 `/api/auth/me` 와 과거 댓글이
> **같은 값으로 함께 움직인다.** "과거 글 소유 판정이 전부 깨진다"·"남의 글에 버튼이 뜬다"는 발생하지 않는다.
> 남는 실체는 "동명이인이 불가능하다는 보장에 소유 판정을 의존한다"는 설계 취약성뿐이다 → P3.

- **현상.** 게시물·댓글 응답 어디에도 작성자 식별자가 없다. `authorNickname` 문자열뿐이다.
- **결과.** 클라이언트가 "내 글"을 판정할 방법이 닉네임 비교밖에 없다. 닉네임을 변경하면
  (`PATCH /api/auth/me/nickname`은 실제로 제공된다) **과거 글·댓글의 소유 판정이 전부 깨진다.**
  수정·삭제 버튼이 사라지거나 남의 글에 뜬다.
- **왜 프론트로 못 고치는가.** 응답에 없는 정보는 만들 수 없다. `403 FORBIDDEN`을 최종 권위로 두는
  현재 방식은 "눌러 보고 실패하면 안다"는 것이라 버튼 표시 자체를 옳게 만들지 못한다.
- **요청.** 게시물·댓글 응답에 `authorId`(회원 PK)를 추가한다. `GET /api/auth/me`가 이미 `id`를 주므로
  클라이언트가 정확히 비교할 수 있다.

### C-2 [P1] `PATCH /api/community/posts/{postId}`가 `instrumentId` 생략 시 종목 태그를 삭제한다

- **현상.** `api-contracts.md:293`이 `instrumentId`를 생략하거나 `null`로 보내면 **기존 태그를 해제한다**고
  명시한다. 즉 제목만 고치려는 요청이 태그를 지운다.
- **결과.** PATCH의 의미론(부분 수정) 위반이다. 모든 클라이언트가 "수정 전 값을 다시 실어 보내기"를
  기억해야 하며, 한 번 잊으면 조용한 데이터 손실이다. 변경 이력이 없어 되돌릴 수 없다.
- **요청.** 둘 중 하나로 확정한다.
  1. `instrumentId` 키가 **없으면 보존**, 명시적 `null`이면 해제 (JSON Merge Patch 관례)
  2. 또는 전체 교체임을 계약에 못박고 메서드를 `PUT`으로 바꾼다

### C-3 [P1] 부모 댓글 삭제가 타인의 대댓글까지 CASCADE로 지운다

> **ALREADY-TRACKED — P1 유지, 다만 "우리가 발견"이 아니다.**
> `022-community-enhancement/spec.md:76`이 **"부모 댓글 삭제 시 자식 처리: 함께 삭제 vs 내용 블라인드
> 처리(예: \"삭제된 댓글입니다\") 중 plan.md 에서 확정한다"** 로 적어 두었다 — 우리가 제안한 tombstone 이
> 이미 게이트의 두 후보 중 하나다. 이슈는 "새 결함 신고"가 아니라 **R-0 형식(추적 항목 인용)** 으로 써야 한다.
> 실체는 남는다 — CASCADE 를 고른 사유가 기록돼 있지 않고, 결과가 `spec:19`("남의 대댓글을 지우려 하면
> 거부당한다")와 충돌한다.

- **현상.** `DELETE /api/community/comments/{commentId}`가 자식 대댓글을 `ON DELETE CASCADE`로 함께 삭제한다.
- **결과.** 내 댓글을 지우면 **다른 회원이 쓴 대댓글이 예고 없이 사라진다.** 그 회원에게는 자기 글을
  지킬 방법도, 삭제됐다는 통지도 없다.
- **요청.** 자식이 있는 부모 댓글은 tombstone(내용만 "삭제된 댓글입니다"로 치환, 행 유지)으로 처리한다.
  일반적인 게시판 관례이며 자식 소유자의 데이터를 보존한다.

### C-4 [P1] 댓글 조회에 페이지네이션이 없다

> **IMPRECISE — P1 → P3.** 실제 데이터 손실이나 기능 불가가 아니라 규모가 커질 때의 성능 문제다.
> 또 요청이 선례로 든 `GET /api/orders` 는 커서 방식인데, **같은 커뮤니티 도메인의 게시물 목록은
> `page`·`size` 오프셋**(`api-contracts.md:283`)이다. 도메인 내 일관성을 따르려면 오프셋이 맞다.
> 프론트는 현재 전부 렌더하되 총 개수를 `countComments`(부모+대댓글)로 정확히 센다.

- **현상.** `GET /api/community/posts/{postId}/comments`가 bare array이고 개수 상한이 문서에 없다.
  COM-005로 `replies` 중첩이 추가된 뒤에도 그대로다.
- **결과.** 댓글이 많은 글에서 응답 크기가 무한히 커진다. 중첩이 생겨 배열 하나에 담기는 총량이 더 늘었다.
- **요청.** 부모 댓글 기준 커서 페이지네이션을 추가한다
  (`GET /api/orders`·`/api/journal`이 이미 쓰는 방식과 동일하게).

## ranking

### R-0 [P1] Redis ZSET 유실 시 재구성 경로가 없다 — 조용히 틀린 값을 반환한다

> **spec 014-ranking 정본 확인분 (2026-08-08 정정).** 이 항목은 spec이 스스로
> **"RANK-001에도 동일하게 남아 있는 미해결 Decision Gate"**(spec:115)라고 적어 둔 것이다.
> 우리가 새로 발견한 것이 아니라 백엔드가 알면서 미뤄 둔 항목이므로, 별도 이슈로 올리기만 하면 된다.

- **현상.** 순위·금액 모두 시장별 ZSET `ranking:{market}`(예: `ranking:STOCK`)에서 읽는다(spec:22).
  실현손익의 정본은 MySQL `accounts.realized_pnl`이고 ZSET은 파생 데이터인데(spec:13·52),
  **ZSET을 정본으로부터 재구성하는 배치·기동 훅이 없다.** RANK-001(이슈 #187)에서 범위 제외(spec:24·61),
  RANK-002(이슈 #233)에서도 동일하게 제외(spec:115·117).
- **결과 — 실패 양상이 두 가지이고 위험한 쪽은 "성공"이다.**
  1. **Redis 서버 장애** → `500 INTERNAL_ERROR`. 눈에 보이므로 그나마 안전하다(→ R-2).
  2. **Redis는 살아 있고 ZSET만 유실·초기화** → API가 **200으로 정상 응답한다.**
     `GET /api/rankings`는 **빈 목록**(전 회원이 "매도 이력 없음"으로 취급돼 제외),
     `GET /api/rankings/me`는 `rank: null` + **`realizedPnl: 0`**.
     spec:111이 `realizedPnl`을 DB가 아니라 **ZSET score에서 채운다**고 명시하므로,
     실제로 DB에 실현손익이 있는 사용자에게 0원이라고 보고한다.
     **오류가 아니라 틀린 숫자**라서 클라이언트도 사용자도 유실 사실을 알 방법이 없다.
- **요청.** `accounts.realized_pnl`에서 `ranking:{market}`을 재구성하는 배치 또는 기동 훅을 만든다.
